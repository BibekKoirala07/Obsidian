## PHASE 1 — Become “Hard to Reject” (0–6 months)

**Goal:**

> “This person can safely build and run backend systems.”

### 🔹 Tech Stack (lock this)

- **Primary:** TypeScript + NestJS
    
- **Secondary (thinking tool):** Java (DSA only)
    
- **Database:** PostgreSQL
    
- **Infra basics:** Docker, Linux
    
- **Cache/Queue:** Redis, BullMQ
    


### 🔹 What you must _actually_ be good at

Not tutorials. Not buzzwords.

#### Backend

- Auth (JWT, refresh tokens)
    
- RBAC
    
- Pagination, filtering, sorting
    
- Idempotency
    
- Background jobs
    
- Rate limiting
    
- Error handling & logging
    

#### Database

- Indexes (B-tree deeply)
    
- Query plans
    
- Joins cost
    
- Transactions
    
- Isolation levels
    

#### DSA (INTERVIEW LEVEL, not olympiad)

- Arrays, strings
    
- HashMap
    
- Stack / Queue
    
- Trees (BST, traversal)
    
- Graph BFS/DFS
    
- Binary search
    

Java only. Period.

---

### 🔹 Output (non-negotiable)

You must **produce**:

#### 1 Serious Project (this matters)

A **boring but real backend**:

Example:

> Multi-tenant SaaS API  
> Auth, roles, billing mock, background jobs, caching, audit logs

Must include:

- NestJS
    
- Postgres
    
- Redis
    
- Clean README
    
- System diagram
    

This alone separates you from 90%.

## PHASE 2 — Interview-Ready Engineer (6–12 months)

**Goal:**

> “This person can pass US interviews.”

This is where most people fail.

---

### 🔹 DSA (minimum viable)

- 100–150 problems total
    
- Mostly **medium**
    
- You should **explain**, not just code
    

If you can:

- Talk through trees
    
- Explain time/space
    
- Debug calmly
    

You’re ready.

---

### 🔹 System Design (CRITICAL)

US companies care more about this than LeetCode.

You must understand:

- Monolith vs microservices
    
- Load balancing
    
- Caching strategies
    
- DB sharding (conceptual)
    
- Message queues
    
- Event-driven design
    

### 🔹 Resume (US-style)

- Impact-driven
    
- Numbers
    
- No fluff
    
- No “worked on”
    

Bad:

> Worked on APIs

Good:

> Designed auth system used by 50k users, reduced support tickets by 30%

❌ Fiverr
